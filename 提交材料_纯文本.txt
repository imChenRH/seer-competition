[1] 开题报告：工业场景分拣配送一体化人形机器人
================================================================================

Part 1：命题前置分析与洞察
--------------------------

一、行业拐点已至：从"能不能动"到"敢不敢用"

据 GGII 预测，2025 年国内人形机器人出货量约 1.8 万台，同比增长超 650%，头部企业年产能已跃升至万台级别。但产能爆发背后有一个关键断层：即便头部企业搬运任务成功率已达 99%，单台效率仍仅为人工的 30%-50%——"能跑 demo，规模化替人尚早"。刚落幕的 WAIC 2026 上，人形机器人的展示重点已从跳舞翻跟头转向拆垛、上料、分拣、搬运等真实工厂作业，行业共识从"能不能动"转向"能不能持续稳定创造价值"。分拣、搬运、质检三类工位因人员流失高、重复性强、工位相对结构化，被共识为最佳切入场景，但真正瓶颈在于软件系统能否在工业约束（节拍、安全、容错）下持续稳定运行。

二、VLA 的工业困境：泛化能力与可控性不可兼得

VLA 模型在 2025-2026 年突破显著——LingBot-VLA 2.0 以 6 万小时真机数据训练并开源，π0.5 首次证明端到端 VLA 可在陌生家庭完成长序列操作。但这些 demo 共享一个前提：失败可重来，无节拍约束，无安全合规要求。工业场景截然不同——将 VLA 从端到端黑箱拆解为感知-理解-规划-控制四个可独立验证的模块后，故障定位时间可从数十小时降至数小时级别。工业要的不是"最聪明的模型"，而是"出了事能查、上线前能验、危险时能停"的系统。我们的判断：端到端 VLA 是科研的理想形态，层次化 VLA（VLA 做技能选择与目标参数生成，经典控制做轨迹执行与安全保护）是工业的当前答案。

三、仙工的独特棋位：全栈能力与平台野心的交汇点

仙工智能不是本体制造商，而是一家"控制器+软件平台"公司——它的战略利益在于让尽可能多的厂商用它的控制器和平台。SRC-5000 是行业标杆级一体化具身智能控制器（156 TOPS AI + RTOS+TSN 实时核），其"一体化具身智能大脑"已获 2026 年 IEEE 机器人与自动化产品创新奖；M4 系统有数千项目验证的调度能力；星云平台已沉淀 1000+ 款机器人型号。WAIC 2026 上仙工 X1-PRO 已演示搬运料箱的完整作业链路——感知到执行的闭环初步打通。同时，2026 年 6 月生效的《人形机器人与具身智能标准体系（2026 版）》及 102 项国家标准，标志着行业进入"可验证、可追溯、可问责"的标准化交付阶段。

核心洞察：这道题的本质不是让参赛者从零造一个 VLA 模型或 AgentOS，而是为仙工设计下一代"具身智能控制器"的软件架构——让 VLA 负责感知到意图的"软决策"，让 AgentOS 负责任务到技能的"编排胶水"，让 SRC-5000 实时核负责运动到安全的"硬执行"。三者分层协作，才能把 VLA 的泛化能力装进工业可控性的框架里。


Part 2：整体解决方案设计
------------------------

1. 方案整体概述

本方案设计一套层次化 VLA + AgentOS 协同的工业分拣配送一体化人形机器人系统。以仙工智能 SRC-5000 为算力与实时控制基座，以 M4 为集群调度中枢，以 AgentOS 为任务与技能编排中间层，在轮式人形机器人 X2-PRO 上构建从自然语言指令到物理动作执行的全闭环。

核心设计原则：VLA 做它擅长的（感知理解+策略选择），经典控制做它擅长的（轨迹执行+安全保护），AgentOS 做两者之间缺失的那一层（任务编排+状态管理+异常恢复）。VLA 的输出不是关节角度，而是"技能选择 + 目标参数"——这一定位从根本上解决了 VLA 在工业场景的可控性问题。

2. 整体架构与核心功能模块（四层架构）

系统自顶向下分为四层，每层有明确的接口边界：

第一层：交互理解层（自然语言 → 结构化任务图）

操作员以自然语言下达指令（如"A 区红色料箱分拣至 B 线 3 号工位，优先级高，30 分钟内完成"）。该层基于 M4 AI 助手的多模态大模型底座，将指令解析为结构化任务图（Task Graph），每个节点包含：任务类型、目标物体描述、源/目的位置、时效约束、优先级。任务图下发至 AgentOS 编排层。

设计说明：自然语言理解在系统中分两个粒度——M4 负责粗粒度的"任务级"理解（做什么任务、在哪做、优先级），VLA 负责细粒度的"技能级"理解（在具体场景中如何执行技能指令）。这一分工避免了单个模型同时处理全局调度语义和局部操作语义的复杂度。

第二层：AgentOS 编排层（任务图 → 技能序列 + 监控恢复）——系统核心创新

AgentOS 维护一个技能库（Skills Library），每项技能是一个可独立验证的操作原语（导航至、定位物体、抓取、放置、扫码、称重、异常上报），并包含前置条件（如"物体在视野内"）、后置条件（如"物体在夹爪中"）、资源需求（如"占用右臂"）和安全边界（如"负载在机器人额定范围内"）。

AgentOS 的四大核心功能：
- 任务分解：将任务图节点映射为技能序列，基于约束推理与前条件链闭合的层次化任务规划，确保技能间前置条件链闭合。
- 状态记忆：维护场景图谱（Scene Graph），记录物体位置、机器人状态、任务进度。VLA 执行每步后，AgentOS 根据感知结果增量更新图谱。
- 异常恢复：Fallback 策略库覆盖四大类异常场景（感知失败、操作失败、环境异常、系统异常）。如抓取失败：微调位姿重试 → 切换视角重新识别 → 上报人工介入。恢复策略可嵌套，避免单点失败导致任务中断。
- 工具调用：对接电梯、输送线、自动门等外部设备，统一管理通信协议和超时重试。

第三层：VLA 执行层（技能 + 观测 → 目标参数 → 动作验证）

这是层次化 VLA 的核心落位。VLA 模型的输入是当前观测（RGB-D + 力觉 + 激光雷达）与 AgentOS 下发的当前技能指令（如"抓取 A 区红色料箱"），输出不是关节角度，而是技能参数：物体 6D 位姿估计、抓取点候选区域、放置目标位置、运动方向向量。

VLA 输出目标参数后，进入"生成→验证→执行"的闭环控制流水线：
1. Skill Policy（经典运动规划器 + 力控伺服模块）基于 VLA 参数生成候选轨迹与关节指令；
2. 候选轨迹经过三层安全验证：
   - 运动学可行性检查（关节限位、工作空间可达性）
   - 动力学碰撞检测（基于实时点云模拟轨迹扫掠体，障碍物距离 < 安全阈值则否决）
   - 人机安全距离校验（轨迹扫掠体与人体检测区域的干涉检查，1.2m 内自动降速至安全模式）；
3. 通过验证的指令由 SRC-5000 的 RTOS+TSN 实时核（时钟抖动 < 30μs）通过 EtherCAT 总线下发执行；未通过则触发对应 Fallback 策略。

第四层：M4 协同调度层（多机调度 → 全局优化 → 数字孪生）

M4 作为顶层调度引擎，管理多台人形机器人与既有 AMR、输送线的协同作业。支持百万级库位、十万级点位调度，动态派单、路径优化、宕机自动恢复。M4 的 AI 助手接收全局任务指令，将任务分配给 AgentOS 实例（每台机器人一个 AgentOS 实例），并监控全局任务进度与资源冲突。

3. 核心创新点

创新一：层次化 VLA 架构。将 VLA 定位为"技能参数生成器"而非"动作生成器"，在 VLA 输出与物理执行之间插入安全验证层和 Skill Policy 层。既保留了 VLA 的视觉-语言泛化能力，又确保了工业可控性。这是区别于端到端 VLA demo 方案的关键差异。

创新二：AgentOS 作为 VLA 与工业系统之间的适配层。AgentOS 不替代 VLA 也不替代 M4，而是填补两者之间的空白——VLA 擅长"看到→想到"，M4 擅长"调度→管理"，AgentOS 负责"拆解→编排→监控→恢复"。三者的分工边界清晰，接口可通过标准化协议定义。

创新三：技能即模块（Skills-as-Modules）的工业知识沉淀机制。每项技能是原子化的操作原语，配置了前置条件、后置条件、资源需求和安全边界。新工序上线时，AgentOS 通过重组已有技能而非重新编程来适配，切换时间从天级缩短至小时级。技能库可跨行业复用，形成仙工平台的核心知识资产。

创新四："生成→验证→执行"闭环 + Fallback 策略库的工业级容错体系。VLA 输出目标参数 → Skill Policy 生成候选轨迹 → 三层安全验证（运动学→碰撞→人机安全）→ 通过则执行，不通过则触发 Fallback。整套机制满足 ISO 10218-1 可追溯要求——任何故障可定位到具体验证环节。

4. 落地预期价值

单台搬运任务成功率：当前行业 95%-99%（优必选 Walker S2 汽车制造场景），本方案目标 >= 99.5%（在同类场景下）。
单台效率 vs 人工：当前 30%-50%，目标 60%-80%。
多机协同产线效率提升：目标 30%+。
新工序切换时间：从数天至数周（传统离线编程），压缩至小时级（技能在线重组）。
故障定位时间：从数十小时（端到端 VLA 行业实践参考值），压缩至数小时级（模块化可追溯架构）。

5. 落地可行性与可推广性

可行性：仙工已具备三大落地条件——SRC-5000 的 156 TOPS AI 算力 + RTOS 实时核为层次化 VLA 提供了异构计算基座；M4 系统数千项目的调度能力可直接承载多机协同需求；星云平台 1000+ 款型的机器人生态为"一脑多机"泛化提供了天然验证场。方案不引入全新硬件，全部建立在仙工现有产品线上。此外，《人形机器人与具身智能标准体系（2026 版）》设定的工业算力（≥500 TOPS）、续航（≥6h）、响应时间（≤200ms）等指标，为方案的技术参数选择提供了国家标准锚点。

推广路径：第一阶段，在 3C 电子、汽车零部件的仙工标杆客户中落地人形机器人分拣配送场景，积累操作类技能库和异常恢复策略；第二阶段，将验证过的技能库和 AgentOS 配置沉淀为标准化软件模块，通过星云平台向半导体、医药、食品等行业复制（操作类技能可直接迁移至同类人形构型，导航类/交互类/系统类技能可跨构型复用）；第三阶段，形成"控制器 + M4 + AgentOS + 行业技能包"的产品矩阵，让集成商可以在星云平台选配机器人本体的同时选配行业技能包（不同构型的机器人加载不同子集的技能），实现从"卖控制器"到"卖智能"的商业模式升级。

[2] 补充材料 01：VLA架构选型分析
================================================================================

核心问题：端到端 VLA、模块化 VLA、层次化 VLA 三种架构范式，在工业分拣配送场景下各有什么优劣？我们为什么选择层次化 VLA 作为方案的技术路线？


一、三种架构的本质区别

说明：学术界对 VLA 架构的主流分类为"端到端 VLA"与"模块化 VLA"两大类。本文在此基础上将模块化 VLA 进一步细分为"传统管道式模块化"和"层次化模块化（Hierarchical VLA）"，后者是本方案选用的技术路线。以下三种架构的并列比较，是为了分析的便利性，不代表行业共识分类标准。

端到端 VLA：一个神经网络，像素/文字进，关节角度出，中间没有人类可读的表示层。代表性模型：RT-2、π0.5、OpenVLA、LingBot-VLA 2.0。

模块化 VLA：VLA 负责理解+规划，动作由下游模块（控制策略/运动规划器）执行，中间有明确接口。各模块独立开发、独立验证。

层次化 VLA（Hierarchical VLA）：模块化 VLA 的一种特定设计模式——VLA 负责高频多变的"软决策"（技能选择+目标参数的生成），经典控制负责低频确定的"硬执行"（轨迹跟踪+力控伺服）。关键区别在于 VLA 不直接输出动作指令，而是输出受约束的"意图参数"。

架构示意：
  端到端 VLA:  [画面+指令] → 一个巨型模型 → [关节角度]
  模块化 VLA:  [画面+指令] → VLA模型 → [任务图/子目标] → [抓取][运动规划][力控] → 关节指令
  层次化 VLA:  [画面+指令] → VLA模型 → [技能选择+目标参数] → [Skill Policy] → 关节指令


二、端到端 VLA 的优劣分析

优势：
1. 没有信息瓶颈：模型内部保留全部感知信息（包括"物体表面有水渍很滑"这类隐式线索），不需要在模块边界做有损压缩。
2. 动作流畅度极好：端到端 VLA 学到的隐式"恢复"能力——遇到偏差时自主微调，不依赖外部重规划。在 π0.5 等模型的公开 demo 中有明显体现。
3. 泛化潜力最大：当训练数据足够大时，能在全新场景输出"合理"动作。

劣势（工业场景致命短板）：
1. 不可解释：抓取失败后无法区分是"识别错"还是"规划错"还是"控制错"。不满足 ISO 10218-1 可追溯要求。
2. 无法表达不确定性：总是输出一个动作，不会说"我没见过这个物体，不知道怎么处理"。
3. 验证不完备：输入空间（所有可能的图像+语言组合）是无穷的，无法在上线前穷举验证安全性。
4. 长序列短视：每步基于当前观测决策，没有显式全局计划。


三、模块化 VLA 的优劣分析

优势：
1. 可追溯：每个模块有明确输入输出，事故后可定位故障模块。
2. 可约束：安全规则可精确插在模块间（如"料箱重量 < 负载上限"的硬拦截）。
3. 可增量开发：新操作只需添加新技能模块，VLA 理解层不用改。

劣势：
1. 信息在模块边界丢失：感知模块输出"红色料箱"，丢掉了"表面反光、凹陷、标签翘起"等细节。
2. 接口僵化：人类定义的接口可能漏掉关键信息通道。
3. 反应速度不如端到端：感知→规划→控制串行延迟，不适合动态抓取。


四、我们的选择：层次化 VLA（Hierarchical VLA）

分工逻辑：

                  VLA（软决策层）                Skill Policy（硬执行层）
  做什么          物体识别、意图理解、技能选择、   轨迹规划、力控伺服、碰撞检测、
                  目标参数生成                   安全保护
  特点            需要泛化、处理变化、             需要确定性、实时性、安全性
                  可容忍一定不确定性
  运行在哪        SRC-5000 的 156TOPS AI 芯片    SRC-5000 的 RTOS+TSN 实时核
  更新频率        可迭代更新（LoRA微调、联邦学习） 出厂固化（严格验证后不轻易改动）

为什么这样选？
1. VLA 做它最擅长的：视觉理解、语义理解、策略选择——这些是传统视觉+规则系统做不好的。
2. 经典控制做它最擅长的：轨迹跟踪、力控、碰撞检测——这些是 VLA 做不好但传统控制做得很成熟的。
3. 与仙工 SRC-5000 硬件天然对齐：156TOPS AI 芯片 + RTOS+TSN 实时核 + EtherCAT 总线。
4. 安全边界清晰：VLA 输出"意图"而非"动作"，即使 VLA 出错，硬件安全层仍有最后一道防线。


五、结论

- 端到端 VLA 是科研的理想形态，层次化 VLA 是工业的当前答案。
- 题目选 VLA 做控制核心，不是因为端到端比模块化更先进，而是 VLA 的视觉-语言-动作统一建模能力是传统"感知→规划→控制"管道做不到的。
- 但这不意味着要把安全验证和运动控制也塞进 VLA。

前瞻：VLA 与 World Action Model 的融合趋势

2026 年的一个显著技术趋势是 VLA 与世界动作模型（World Action Model, WAM）的融合。代表性进展：

- InternVLA-A1.5（上海 AI Lab，2026.07）：在 VLA 框架中引入"隐式预见"（latent foresight），让模型在动作生成前预测未来状态，六项仿真基准全部最佳。
- Being-M0.7（智在无界，2026.07）：全球首个面向人形机器人全身移动操作的隐式世界动作模型，采用"低频规划+高频控制解耦"——即高层生成未来状态规划，低层动作专家以高频生成可执行动作。
- Kairos（ACE Robotics，2026.06）：以 4B 参数的世界模型在 LIBERO-Plus 上首次超越所有 VLA 系统（89.0 vs ACoT-VLA 88.0）。

二、Fallback 策略库

2.1 策略分类与触发机制

Fallback 策略按异常来源分为四大类。各类策略的数量随场景积累而增长，以下为分拣配送场景的首版覆盖：

  异常检测（AgentOS 监控）
  连续失败 N 次 / 超时 / 置信度 < 阈值
  ├── 感知失败类 (7项)
  ├── 操作失败类 (6项)
  ├── 环境异常类 (5项)
  └── 系统异常类 (5项)

参数说明：以下表格中的数值阈值（如 0.6 置信度、50 lux 等）为初始设计建议值。标注来源的数值（如 1.2m 人机安全距离参考 ISO/TS 15066）有标准依据，其余为基于经验的初步设定，需在真实部署中实测验证。夹持力相关参数已与物料标签系统联动，不再以固定数值硬编码。

2.2 感知失败类（7 项）

  FB-P01 目标物体未识别 | 连续3帧置信度<0.6 | ①调整相机曝光 ②切换侧方视角 ③查询WMS验证在库 | 重试3次 | 通知M4改派其他机器人
  FB-P02 位姿估计置信度低 | 置信度0.6~0.85 | ①微调观测角度(±15°) ②启用多视角融合 ③切换高分辨率 | 重试2次 | 低置信度+力控搜索模式
  FB-P03 物体被遮挡 | 可见像素<50%模板 | ①侧移0.3m换视角 ②末端相机近距离观察 ③请求邻近机器人辅助 | 重试2次 | 标记暂不可操作，优先处理其他物体
  FB-P04 光照异常 | 亮度<50 lux或>10000 lux | ①开启主动补光 ②切换红外模式 ③等待光照稳定 | 重试2次 | 降低置信度阈值至0.7，加强力控保护
  FB-P05 物体类别置信度不足 | Top-1与Top-2差<0.15 | ①读条码交叉验证 ②称重对比 ③查询任务上下文推断 | 重试2次 | 按"未知物体"上报人工
  FB-P06 传感器不一致 | RGB-D与雷达偏差>5cm | ①优先信任雷达 ②重新标定外参 ③切换至单一传感器 | 重试1次 | 仅使用雷达做碰撞检测
  FB-P07 相机镜头污损 | 连续多帧固定位置模糊 | ①切换备用相机 ②上报维护请求 ③无备用则立即安全停止 | 重试1次 | 有备用：切换后降速执行。无备用：严禁进入无视觉运行状态——实时核接管，立即减速停靠至最近安全位置，触发声光报警，向M4上报故障并等待人工维护。工业分拣配送场景中失去视觉意味着无法安全导航、人机距离感知和场景变化检测，继续移动构成严重安全风险

2.3 操作失败类（6 项）

  FB-M01 抓取滑落 | 力传感器检测位移>5mm | ①查询物料F_max；未达F_max则加力10%重试 ②若已逼近F_max(如3C裸PCB/电芯等脆性物料)则放弃加力→微调抓取点(±3mm) ③切换备选策略(改夹为托/改侧面为顶部吸取) | 重试3次 | 上报AgentOS，人工远程接管
  FB-M02 放置不对齐 | 位置偏差>1cm | ①提起重新对齐 ②启用视觉伺服精调 ③降低放置速度至50% | 重试2次 | 放置于暂存区，通知输送线暂停
  FB-M03 力控超限 | 末端接触力突增>安全阈值 | ①立即停止 ②后退2cm ③以10%额定力慢速重试 | 重试2次 | 停止当前操作，人工检查碰撞原因
  FB-M04 双臂力失衡 | 双腕力传感器差值>20% | ①暂停运动 ②高侧卸力至平衡 ③重新同步 | 重试2次 | 切换为单手操作模式(如负载允许)
  FB-M05 扫码失败 | 3s内未成功读取 | ①调整距离(±10cm) ②切换补光 ③尝试不同角度 | 重试3次 | 拍摄高清图片上传MES，人工录入
  FB-M06 传送带同步超时 | 2s内未收到PLC就绪 | ①等待5s重新握手 ②查询输送线状态 ③通知M4 | 重试2次 | 物体暂存缓冲区，执行下一任务

2.4 环境异常类（5 项）

  FB-E01 路径被阻挡 | 障碍物占据路径>15s | ①等待10s ②请求障碍物识别 ③触发M4重新规划 | 重试3次 | 执行动态绕行或等待人工清障
  FB-E02 工位被占用 | 目标工位有人或机器人 | ①排队等待 ②请求M4调度备用工位 ③升级任务优先级 | 重试2次 | 改为邻近工位，通知MES更新物料路由
  FB-E03 地面异常 | IMU检测倾斜>5° | ①降速至0.3m/s ②高精度SLAM重定位 ③倾斜持续则停 | 重试1次 | 停止移动，进入安全模式，上报维护
  FB-E04 人机安全距离触发 | 人体进入1.2m区域 | ①立即降速 ②语音提示避让 ③人员离开后3s自动恢复 | 持续 | 人员持续在0.8m内30s则静止并呼叫人工
  FB-E05 环境布局变更 | 场景图谱与观测差异>30% | ①暂停操作 ②调用PER-04全面重建图 ③重建场景图谱 | 重试2次 | 降级为探索模式逐步重建环境认知

2.5 系统异常类（5 项）

  FB-S01 VLA推理超时 | 推理超过预设时限(需在目标硬件上实测后设定) | ①降分辨率重试 ②重试期间实时核指令机械臂保持有源悬停(力控回路维持夹持状态不松脱，不执行新动作) ③重试仍超时则移交实时核安全状态机 | 重试2次 | 实时核接管后：若在操作中则回退至预设安全位姿；若在移动中则降速导航至最近安全停靠点。上报AgentOS改派任务。不套用历史缓存参数——动态场景中上一轮推理结果对应的环境状态可能已改变，盲目使用有物理碰撞风险
  FB-S02 总线通信异常 | EtherCAT连续心跳超时 | ①触发总线状态诊断 ②关节抱闸保持 ③通信恢复后状态校验再继续 | 重试2次 | 立即停止运动，进入安全状态，通知M4改派
  FB-S03 内存泄漏告警 | 非核心节点内存>85% | ①自动重启受影响节点 ②持续告警则24h内计划性重启 | 重试3次 | 全系统在任务间隙计划性重启
  FB-S04 电量不足 | SOC<15% | ①完成当前原子操作后停止接收新任务 ②导航至充电桩 ③通知M4改派 | 重试1次 | 立即执行自动回充
  FB-S05 M4连接断开 | 心跳包丢失>5s | ①启用本地离线模式 ②完成当前任务后等待重连 ③3分钟内未恢复则进入安全模式 | 重试3次 | 完成当前任务后停止，等待人工干预


三、Fallback 嵌套调用示例

以"料箱分拣"任务中抓取滑落为例：

  [任务: 抓取 A-3 工位红色料箱]
      │
      ▼
  [MAN-01 抓取技能执行]
      │
      ├── 成功 ──→ [上报 AgentOS: 技能完成, 更新场景图谱]
      │
      └── 失败: FB-M01 触发（夹爪力传感器检测到位移 > 5mm）
              │
              ▼
          [L1: 查物料F_max；未达上限则加夹持力10%重试]
              │
              ├── 成功 ──→ [记录: 原夹持力不足, 更新该物体抓取参数]
              │
              └── 失败（或已达F_max上限跳过L1）
                      │
                      ▼
                  [L2: FB-P02 触发, 重新估计位姿]
                      │
                      ├── 新位姿置信度 > 0.85 ──→ [以新位姿重试 MAN-01]
                      │     └── (若再次失败, 跳过已尝试的L1, 直接进入L3)
                      │
                      └── 置信度 < 0.85
                              │
                              ▼
                          [L3: 低置信度+力控搜索模式]
                              │
                              ├── 成功 ──→ [记录: 该物体需改进感知模型]
                              │
                              └── 失败 ──→ [上报 AgentOS → M4 → 人工介入]

关键设计原则：
- 每级 Fallback 不超过其分配的时间预算（总 Fallback 耗时 ≤ 技能剩余时间预算）
- Fallback 之间可跨类型调用（操作失败 FB-M01 → 感知失败 FB-P02）
- 最终降级总是收敛到安全状态（人工介入 / 静止等待 / 任务移交）


四、时间预算与节拍保障机制

4.1 问题

工业分拣配送场景有严格的产线节拍约束——单个工位的操作时间窗口是固定的。如果 VLA 推理重试或多级 Fallback 嵌套导致单次操作耗时远超预期，会影响整条产线的节拍，甚至导致线停。Fallback 策略不能无限制地重试。

4.2 时间预算模型

AgentOS 在任务分解阶段为每个技能节点分配一个最大允许执行时间（时间预算），该预算来自产线的节拍分配和上下游工序的时间约束。

  任务总时间预算（由产线节拍决定）
    ├── NAV-01 区域导航 ──── 分配: T_nav
    ├── PER-01 物体识别 ──── 分配: T_per
    ├── MAN-01 抓取 ──────── 分配: T_grasp (含 Fallback 子配额)
    ├── NAV-01 区域导航 ──── 分配: T_nav2
    └── MAN-02 放置 ──────── 分配: T_place

每个技能节点的时间预算 = 正常执行时间 + Fallback 容许时间。技能定义模板中的"超时阈值"字段即为此预算的上限。

4.3 Fallback 期间的时间预算检查

在 Fallback 嵌套调用的每一级，AgentOS 实时检查该技能的剩余时间预算：

  [MAN-01 开始, 时间预算 T_grasp]
      │
      ├── 正常执行成功（耗时 t₁）──→ 剩余预算返还任务池
      │
      └── 失败: FB-M01 触发
              │
              ├── 检查: 剩余预算 ≥ T_min_retry ?
              │     ├── 是 → [L1: 加夹持力重试]
              │     └── 否 → 跳过所有后续 Fallback, 直接执行降级策略
              │
              └── L1 失败
                    │
                    ├── 检查: 剩余预算 ≥ T_min_relocalize ?
                    │     ├── 是 → [L2: 重新估计位姿]
                    │     └── 否 → 跳过, 直接执行降级策略
                    │
                    └── L2 失败 → [L3: 力控搜索]
                          │
                          └── 剩余预算不足 or L3 失败 → [降级策略]

4.4 降级策略（节拍保底）

当剩余时间预算不足时，AgentOS 直接执行降级策略：

  MAN-01 抓取: 正常路径 L1→L2→L3 → 降级: 物体标记"当前不可操作"，推送暂存区，M4调度其他机器人或人工处理
  PER-01 识别: 正常路径 多视角融合 → 降级: 以当前低置信度结果+力控保护模式尝试操作
  NAV-03 避障: 正常路径 等待+重规划 → 降级: 执行原路径降速通过，增强实时碰撞检测灵敏度

4.5 与技能定义模板的衔接

技能定义模板中的"超时阈值"字段即为此技能的时间预算。在部署到具体产线时，该阈值根据产线节拍、上下游工位的时间约束和该技能的历史耗时分布来设定。AgentOS 在运行时使用该阈值做实时预算检查。

4.6 设计约束

- 降级策略的执行时间必须是确定的、可预测的（降级的目的是保节拍，不能再触发嵌套 Fallback）
- 降级策略不追求"最优执行"，只追求"安全且按时完成"
- 连续的降级触发会被 AgentOS 上报给 M4，作为产线瓶颈或模型能力预警信号
- Fallback 路径的单向收敛约束：在单次原子任务执行周期内，如果某一 Fallback 层级（如 L1 加力重试）已执行并失败，且后续通过 L2 重新估计位姿后再次触发 MAN-01 重试，若 MAN-01 再次失败，调度层必须跳过已尝试过的 L1，直接进入 L3 或降级策略——禁止在 MAN-01→L1→L2→MAN-01 的路径上形成重复循环

二、各方案技术路线的本质差异

2.1 优必选 Walker S2：规模优先、工程驱动的渐进路线
核心思路：不做 VLA 模型创新，通过"群脑网络"实现多机器人协作，用工程手段推动规模化落地。优势：14 亿元订单证明客户认可，搬运任务 99% 成功率。劣势：未深度融合 VLA/大模型，长期泛化天花板受限；双足续航~2h。与本方案差异：优必选"用工程确定性对冲技术不确定性"，我们"用分层架构把 VLA 能力安全地装进工业框架"。

2.2 蚂蚁灵波 LingBot-VLA 2.0：端到端、追求通用泛化
核心思路：做一个"通用具身大脑"，一套模型驱动多种机器人和场景。优势：跨构型泛化最强(20种)，数据量最大(6万小时)，推理延迟最低(<130ms)。劣势：端到端架构的工业安全性和可追溯性未公开验证。与本方案差异：蚂蚁灵波追求"通用性天花板"，我们追求"工业可控性地板"。

2.3 优艾智合 FabriX + 隙锋：场景深度优先、制造业深耕
核心思路：做"工业大模型"深度融合制造场景。优势：800+场景和70%复购率是最扎实的商业化证明；WAIC展示5台隙锋+1台搬运机器人线边仓分拣配送；4000台认购(29.9-49.9万定价)。劣势：FabriX是调度大模型而非VLA，泛化是场景内迁移而非跨域泛化。与本方案差异：优艾智合"用大模型优化调度层"，我们"用VLA革新执行层"——两者可互补。

2.4 星动纪元 ERA-42 + L7：端到端 VLA 原生 + 双足全尺寸
核心思路：从零设计端到端VLA+全尺寸双足人形。优势：VLA与硬件协同设计，12自由度灵巧手+腰部3DoF。劣势：双足+端到端VLA组合风险最高，目前仅验证物流仓储。与本方案差异：星动纪元"硬件+模型原生协同"，我们"成熟平台+层次化VLA软件"——工程风险更低。

三、本方案的差异化定位

一句话定位："在仙工成熟硬件和调度平台之上，用层次化 VLA 做工业可控的智能执行。"

三个差异化支柱：
1. 架构差异化：层次化 VLA 是第三条路——所有竞品要么端到端VLA要么非VLA。VLA负责泛化，经典控制负责安全，这不是妥协而是主动设计选择。
2. 平台差异化：深度嵌入仙工 SRC-5000 + M4 + 星云平台，这在仙工赛道中是独特的适配优势。
3. 商业模式差异化：技能库作为平台资产——可复制到1000+款型，形成网络效应。

我们与竞品的客观差距：
- vs 蚂蚁灵波：VLA数据量和通用性远不及(6万小时vs从零开始)
- vs 优必选：工程化部署经验差距巨大(14亿订单/500台交付vs纸面设计)

- vs 星动纪元：VLA-硬件协同设计不如原生方案(多一层间接性)

[6] 补充材料 05：工业部署关键机制——冷启动、安全审计与硬件映射
================================================================================

本文档回应工业落地的三个关键问题：新场景如何冷启动、事故后如何可追溯、VLA与实时控制在SRC-5000上如何分工。所有参数和流程均为方案设计，具体数值需在真实部署中验证。


一、冷启动策略：从零数据到安全上线的四阶段管道

问题：首次进入新工厂/新工序时没有该场景的VLA标注数据，且工业现场不允许长时间遥控操作数据采集。

核心思路：利用仙工现有资产（星云平台场景库、SRC-5000算力）与仿真技术，实现低人工介入的冷启动，而非依赖长期现场遥操作。

阶段一：仿真预训练（离线，部署前完成）
- 输入：星云平台同类场景历史数据（产线CAD布局、物料规格、工序流程）；目标工厂场景参数
- 方法：在物理仿真环境（如Isaac Sim或仙工Meta-World数字孪生平台）中构建目标场景数字副本，生成分拣-配送全流程合成轨迹数据
- 产出：预训练VLA模型基座 + 预置技能库初始参数
- 优势：不依赖真机运行，不占用产线时间；利用仙工1000+款型历史场景做迁移学习基础

阶段二：离线场景标定（部署首日，数小时级）
- 输入：部署首日在真实工厂拍摄的全景静态图像（多角度RGB-D快照）+ 物料清单和工位布局图
- 方法：离线环境下使用多模态大模型进行物体检测、位姿估计和场景图谱初始化；人工校验关键物料和工位标定结果
- 产出：初始化的场景图谱（Scene Graph）+ 关键物料视觉模板库
- 优势：不依赖云端实时连接（离线完成），人工介入仅在校验环节

阶段三：影子模式安全上线（部署首周）
- 运行方式：机器人由经典控制执行实际作业，VLA模型在后台并行运行但不输出控制指令
- 影子模式的核心目的：验证VLA输出的物理安全性，而非任务成功率。任务成功率只能在VLA实际接管后才能衡量——影子模式下物理世界的行为由经典控制完成，不能将经典控制达成的成功归因于VLA。评估标准为VLA输出的参数全部通过三层安全验证——即VLA提议的动作在物理上是可执行且不触发碰撞/超限/安全距离违规的
- 接管条件：当VLA的安全通过率在连续作业周期中达到设定标准（具体阈值根据工位风险等级确定），AgentOS逐步将对应技能节点从经典控制切换至VLA控制。切换后进入真实任务成功率监控阶段
- 回退机制：切换后如出现VLA特有类型的Fallback触发或任务成功率显著低于经典控制基线，自动回退至经典控制

阶段四：边缘持续微调（长期运行）
- 运行方式：SRC-5000的AI算力核心在任务间隙对VLA模型进行LoRA微调
- 训练数据来源：(1)影子模式阶段的对比差异数据 (2)运行中Fallback触发的失败场景 (3)AgentOS记录的VLA低置信度输出
- 产出：VLA模型针对当前场景持续改进，数据不离厂（隐私/安全合规）
- 优势：形成"运行→积累corner case→微调→提升"的数据飞轮

与仙工现有资产的衔接：
  星云平台1000+款型场景库  → 预训练迁移学习的数据基础
  SRC-5000 156TOPS AI算力  → 仿真数据生成+LoRA微调的算力载体
  Meta-World数字孪生       → 仿真场景构建平台
  M4管理系统               → 影子模式期间的性能监控与A/B切换调度


二、安全审计追溯机制

问题：当机器人在工业场景中发生碰撞、误操作或异常停机时，工厂需要快速判定根因——是VLA推理错误、传感器输入异常、AgentOS状态机死锁，还是底层通信丢包。需满足ISO 10218-1和《人形机器人与具身智能标准体系（2026版）》的可追溯要求。

核心思路：在每个安全关键决策点记录VLA的输出状态、感知输入的关键特征、以及决策链路，使事后追溯可在模块级别定位故障。

三层审计记录：

  审计层级      记录内容                                          故障定位价值
  ───────────── ───────────────────────────────────────────────── ──────────────────────────────────────
  VLA决策层     当前技能指令、VLA输出的Top-3候选参数及置信度、      区分"VLA推理错误"vs"VLA输入异常"
                模型版本标识
  安全验证层    三层验证各自结果、否决的参数或轨迹段、触发的规则    区分"误拒"vs"正确拦截危险参数"
  执行反馈层    力传感器突变曲线、关节力矩异常、EtherCAT通信状态、  区分"外部事件中断"vs"执行层自身异常"
                急停触发时间戳

此外保留关键决策时刻的RGB-D关键帧（压缩格式），仅保留异常前后短时间窗口帧，正常运行帧定期清除。

故障定位流程（逐层排查）：

  异常事件（急停触发 / 碰撞检测 / 力控超限）
      │
      ▼
  [L1: 执行反馈层检查]
      ├── 关节力矩/力传感器曲线异常？ → 硬件/通信故障 (FB-S02, FB-M03)
      └── 正常 → 继续
      │
      ▼
  [L2: 安全验证层检查]
      ├── 验证报了警告但被override？ → 安全策略配置问题
      ├── 验证全部通过但仍然碰撞？ → 验证算法缺陷（如点云盲区）
      └── 正常 → 继续
      │
      ▼
  [L3: VLA 决策层检查]
      ├── 置信度低但未触发Fallback？ → Fallback阈值需调整
      ├── 置信度高但参数实际错误？ → VLA模型泛化失败 (FB-P01, FB-P02)
      └── 正常 → 外部环境突变 (FB-E01, FB-E04)

审计机制不替代Fallback策略库——Fallback处理"运行时怎么恢复"，审计处理"事后怎么排查"。


三、SRC-5000 异构核心的软硬件映射

问题：方案中的VLA需要高算力但可容忍一定延迟，实时控制需要微秒级确定性。两者在SRC-5000上如何分工、如何通信？

核心思路：基于仙工SRC-5000公开规格（156 TOPS AI算力、RTOS+TSN实时核、EtherCAT总线、<30μs时钟抖动），将各模块映射到对应硬件资源，不添加未经证实的OS选型或量化细节。

异构核心分工：

  ┌─────────────────────────────────────────────────────┐
  │              SRC-5000 一体化具身智能控制器               │
  ├─────────────────────────────────────────────────────┤
  │  【AI 算力核心】（156 TOPS，面向推理与规划）              │
  │  · 交互理解层：自然语言指令 → 结构化任务图               │
  │  · AgentOS 编排层：任务分解、技能排序、场景图谱维护       │
  │  · VLA 模型推理：观测 + 技能指令 → 技能参数              │
  │  · 持续学习：任务间隙 LoRA 微调                         │
  │  特点：高吞吐、允许毫秒级延迟、批量处理                   │
  ├─────────────────────────────────────────────────────┤
  │  【实时控制核心】（RTOS + TSN，时钟抖动 < 30μs）          │
  │  · Skill Policy 执行器：轨迹生成、运动规划、力控伺服      │
  │  · 三层安全验证：运动学 → 碰撞检测 → 人机距离            │
  │  · 安全状态机：急停响应、抱闸控制、安全模式切换            │
  │  · EtherCAT 总线主站：关节指令下发与状态反馈              │
  │  特点：确定性延迟、微秒级响应、硬件级安全保护              │
  └─────────────────────────────────────────────────────┘

AI核心与实时核心之间的数据交换必须采用无锁、非阻塞的通信机制（如双缓冲或单写多读环形缓冲区）。VLA输出的技能参数以非阻塞方式写入，实时核心以确定性的周期从最新完成写入的数据区读取——无论AI核心是否正在写入下一帧。如果采用朴素的互斥锁共享内存，AI核心（运行非实时系统）持有锁期间若发生调度卡顿，实时核心将在等待锁释放时被阻塞，破坏其<30μs的时钟抖动保证。无锁设计从根本上消除了这一风险：实时核心永远无需等待AI核心释放任何资源，安全状态机在最坏情况下（AI核心完全崩溃）仍可在最近一次成功写入的有效数据基础上做安全决策，或在数据过期时触发安全停止。

安全隔离原则：
- 实时核心的安全状态机独立于AI核心运行——即使AI核心完全崩溃，实时核心仍能在一个控制周期内完成急停响应
- AI核心输出的参数不是最终执行指令——必须经过实时核心的三层安全验证后才转化为物理动作
- 安全边界清晰：VLA可以"建议"，实时核决定"是否执行、如何执行"

以上映射基于仙工已公开的SRC-5000规格参数。具体实现中的通信协议、内存布局等细节需基于仙工SDK实际API适配——本方案提供架构层面的分工原则，而非特定SDK的实现指南。

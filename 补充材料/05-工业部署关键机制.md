# 补充材料 05：工业部署关键机制——冷启动、安全审计与硬件映射

> 本文档回应工业落地的三个关键问题：新场景如何冷启动、事故后如何可追溯、VLA 与实时控制在 SRC-5000 上如何分工。所有参数和流程均为方案设计，具体数值需在真实部署中验证。

---

## 一、冷启动策略：从零数据到安全上线的四阶段管道

### 问题

VLA 模型的泛化能力依赖于训练数据覆盖。首次进入一个新工厂/新工序场景时，没有该场景的 VLA 标注数据（视觉-语言-动作三元组），且工业现场不允许长时间的遥控操作数据采集。

### 核心思路

**利用仙工现有资产（星云平台场景库、SRC-5000 算力）与仿真技术，实现低人工介入的冷启动，而非依赖长期现场遥操作。**

### 四阶段管道

**阶段一：仿真预训练（离线，部署前完成）**

- 输入：星云平台沉淀的同类场景历史数据（产线 CAD 布局、物料规格、工序流程）；目标工厂的场景参数（工位坐标、料箱尺寸、节拍要求）
- 方法：在物理仿真环境（如 Isaac Sim 或仙工 Meta-World 数字孪生平台）中构建目标场景的数字副本，生成分拣-配送全流程的合成轨迹数据
- 产出：面向目标场景的预训练 VLA 模型（基座）+ 预置技能库初始参数
- 优势：不依赖真机运行，不占用产线时间；利用仙工已有 1000+ 款型的历史场景数据做迁移学习基础

**阶段二：离线场景标定（部署首日，数小时级）**

- 输入：部署首日在真实工厂拍摄的全景静态图像（多角度 RGB-D 快照）+ 已有的物料清单和工位布局图
- 方法：离线环境下（非实时依赖），使用多模态大模型对静态场景进行物体检测、位姿估计和场景图谱初始化；人工校验关键物料和工位的标定结果
- 产出：初始化的场景图谱（Scene Graph）+ 关键物料的视觉模板库
- 优势：不依赖云端实时连接（离线完成），人工介入仅在校验环节，耗时可控

**阶段三：影子模式安全上线（部署首周）**

- 运行方式：机器人由经典控制执行实际作业，VLA 模型在后台并行运行但不输出控制指令
- 影子模式的核心目的：**验证 VLA 输出的物理安全性，而非任务成功率**（任务成功率只能在 VLA 实际接管后才能衡量——影子模式下物理世界的行为由经典控制完成，不能将经典控制达成的成功归因于 VLA）。评估标准为 VLA 输出的参数**全部通过三层安全验证**——即 VLA 提议的动作在物理上是可执行且不触发碰撞/超限/安全距离违规的。通过率统计的是"VLA 输出了多少比例的安全可行动作"
- 接管条件：当 VLA 的安全通过率在连续作业周期中达到设定标准（具体阈值需根据工位风险等级确定），说明 VLA 在这个工位上已具备安全输出的稳定性，AgentOS 逐步将对应技能节点从经典控制切换至 VLA 控制。切换后，进入真实任务成功率监控阶段——此阶段才通过后续感知确认 VLA 的实际任务完成率
- 回退机制：切换后如出现 VLA 特有类型的 Fallback 触发（如 FB-P02 位姿估计低置信度），该技能节点自动回退至经典控制，影子模式继续收集数据。切换后如任务成功率显著低于经典控制基线，同样触发回退

**阶段四：边缘持续微调（长期运行）**

- 运行方式：SRC-5000 的 AI 算力核心在任务间隙对 VLA 模型进行 LoRA 微调
- 训练数据来源：(1) 影子模式阶段积累的对比差异数据 (2) 实际运行中 Fallback 触发的失败场景 (3) AgentOS 记录的 VLA 低置信度输出样本
- 产出：VLA 模型针对当前场景的持续改进，无需数据离厂（隐私/安全合规）
- 优势：形成"运行 → 积累 corner case → 微调 → 提升"的数据飞轮，不依赖外部数据标注服务

### 与仙工现有资产的衔接

| 仙工资产 | 在冷启动中的角色 |
|---------|---------------|
| 星云平台 1000+ 款型场景库 | 预训练迁移学习的数据基础 |
| SRC-5000 156 TOPS AI 算力 | 仿真数据生成 + LoRA 微调的算力载体 |
| Meta-World 数字孪生 | 仿真场景构建平台（如仙工已具备此能力） |
| M4 管理系统 | 影子模式期间的性能监控与 A/B 切换调度 |

## 二、安全审计追溯机制

### 问题

当机器人在工业场景中发生碰撞、误操作或异常停机时，工厂需要快速判定根因——是 VLA 模型推理错误、传感器输入异常、AgentOS 状态机死锁，还是底层通信丢包。这要求系统具备"事后可追溯"的能力，满足 ISO 10218-1 和《人形机器人与具身智能标准体系（2026 版）》安全伦理板块的要求。

### 核心思路

**在每个安全关键决策点记录 VLA 的输出状态、感知输入的关键特征、以及决策链路，使事后追溯可在模块级别定位故障。**

### 三层审计记录

运行时的每一次安全关键决策（技能选择、VLA 参数输出、安全验证结果）在 AgentOS 的状态记忆中也保存一份结构化的审计记录。具体记录以下内容：

| 审计层级 | 记录内容 | 记录的故障定位价值 |
|---------|---------|------------------|
| **VLA 决策层** | 当前技能指令、VLA 输出的 Top-3 候选参数及各自置信度、模型版本标识 | 区分"VLA 推理错误"（低置信度但未触发拒止）vs "VLA 输入异常"（输入图像/指令质量差） |
| **安全验证层** | 三层验证各自的结果（运动学/碰撞/人机距离）、否决的参数或轨迹段、触发的具体验证规则 | 区分"VLA 输出了合理参数但被误拒"vs "VLA 输出了危险参数且被正确拦截" |
| **执行反馈层** | 力传感器突变曲线、关节力矩异常、EtherCAT 通信状态、急停触发时间戳 | 区分"控制执行正常但被外部事件中断"vs "控制执行本身异常" |

此外，保留关键决策时刻的 RGB-D 关键帧（压缩格式），仅保留触发异常前后短时间窗口的帧，正常运行的帧定期清除以控制存储开销。

### 故障定位流程

当发生碰撞/异常停机时，AgentOS 按以下顺序逐层排查：

```
异常事件（急停触发 / 碰撞检测 / 力控超限）
    │
    ▼
[L1: 执行反馈层检查]
    ├── 关节力矩/力传感器曲线异常？ → 硬件/通信故障 (FB-S02, FB-M03)
    └── 正常 → 继续
    │
    ▼
[L2: 安全验证层检查]
    ├── 三层验证中的某一层报了警告但被 override？ → 安全策略配置问题
    ├── 验证全部通过但仍然碰撞？ → 验证算法缺陷（如点云盲区）
    └── 正常 → 继续
    │
    ▼
[L3: VLA 决策层检查]
    ├── 输出参数置信度低但未触发 Fallback？ → Fallback 阈值需调整
    ├── 置信度高但参数实际错误？ → VLA 模型泛化失败 (FB-P01, FB-P02)
    └── 正常 → 外部环境突变 (FB-E01, FB-E04)
```

### 与已有 Fallback 策略库的衔接

审计机制不替代 Fallback 策略库——Fallback 处理"运行时怎么恢复"，审计处理"事后怎么排查"。两者配合：

- Fallback 触发时，AgentOS 在审计记录中标记 Fallback ID（如 FB-M01），并记录触发时的上下文
- 事后排查时，通过 Fallback ID 直接定位到恢复策略的执行链路，判断是恢复策略本身不足，还是底层问题超出了策略覆盖范围

## 三、SRC-5000 异构核心的软硬件映射

### 问题

方案中的四层架构建在不同属性的计算资源上——VLA 需要高算力但可容忍一定延迟，实时控制需要微秒级确定性。两者在 SRC-5000 上如何分工、如何通信？这需要基于仙工公开的硬件规格给出清晰的映射。

### 核心思路

**基于仙工 SRC-5000 公开规格（156 TOPS AI 算力、RTOS+TSN 实时核、EtherCAT 总线、<30μs 时钟抖动），将架构层的各模块映射到对应的硬件资源上，不添加未经证实的 OS 选型或量化细节。**

### 异构核心分工

```
┌─────────────────────────────────────────────────────┐
│              SRC-5000 一体化具身智能控制器               │
├─────────────────────────────────────────────────────┤
│  【AI 算力核心】（156 TOPS，面向推理与规划）              │
│  · 交互理解层：自然语言指令 → 结构化任务图               │
│  · AgentOS 编排层：任务分解、技能排序、场景图谱维护       │
│  · VLA 模型推理：观测 + 技能指令 → 技能参数              │
│  · 持续学习：任务间隙 LoRA 微调                         │
│  特点：高吞吐、允许毫秒级延迟、批量处理                   │
├─────────────────────────────────────────────────────┤
│  【实时控制核心】（RTOS + TSN，时钟抖动 < 30μs）          │
│  · Skill Policy 执行器：轨迹生成、运动规划、力控伺服      │
│  · 三层安全验证：运动学 → 碰撞检测 → 人机距离            │
│  · 安全状态机：急停响应、抱闸控制、安全模式切换            │
│  · EtherCAT 总线主站：关节指令下发与状态反馈              │
│  特点：确定性延迟、微秒级响应、硬件级安全保护              │
└─────────────────────────────────────────────────────┘
```

AI 核心与实时核心之间的数据交换必须采用**无锁、非阻塞的通信机制**（如双缓冲或单写多读环形缓冲区）。VLA 输出的技能参数以非阻塞方式写入，实时核心以确定性的周期从最新完成写入的数据区读取——无论 AI 核心是否正在写入下一帧。如果采用朴素的互斥锁共享内存，AI 核心（运行非实时系统）持有锁期间若发生调度卡顿，实时核心将在等待锁释放时被阻塞，破坏其 <30μs 的时钟抖动保证。无锁设计从根本上消除了这一风险：实时核心永远无需等待 AI 核心释放任何资源，安全状态机在最坏情况下（AI 核心完全崩溃）仍可在最近一次成功写入的有效数据基础上做安全决策，或在数据过期时触发安全停止。

### 安全隔离原则

- 实时核心的安全状态机**独立于 AI 核心运行**——即使 AI 核心上的 VLA 推理或 AgentOS 规划完全崩溃，实时核心仍能在 1 个控制周期内完成急停响应
- AI 核心输出的参数**不是最终执行指令**——必须经过实时核心的三层安全验证后才转化为物理动作
- 安全边界清晰：VLA 可以"建议"，实时核决定"是否执行、如何执行"

### 与仙工产品架构的衔接

以上映射基于仙工已公开的 SRC-5000 规格参数。具体实现中，AI 核心与实时核心之间的通信协议、内存布局、安全状态机的状态定义等细节，需基于仙工 SDK 的实际 API 进行适配——本方案提供的是架构层面的分工原则，而非特定 SDK 的实现指南。
